**Why this is real (verified 2026-08-15 against `origin/main` 088bb61):**
`_list_api_disks` fetches with `control.result("/api/v1/disks")` (raid.py:122), which returns the envelope's `result` payload and discards its `warnings`. When the Disk collector is degraded the control path answers with an empty result **plus** a `DEGRADED_BACKEND_UNAVAILABLE` warning. The wizard sees zero rows and aborts with a bare `"No available NVMe drives found."` — telling the operator there are no drives, when the truth is that nothing could be observed. This is the same class of bug the NFS and RAID-overview screens already fixed by fetching the full envelope with `control.get` and rendering `degraded_banner(env)`; `raid.py` already imports `degraded_banner` (line 36) and uses it at lines 400 and 415. The disk adapter is the one path that still drops it.

Three other call sites use `_list_api_disks` (`raid.py:220`, `raid.py:900`, `spare_pools.py:190`). They are **not** changed: keeping the existing signature and adding a banner-aware sibling avoids three call sites that would have to accept and then discard a value they do not render.

#### 2a — a failed restart must not be audited as `OK`

**Why this is real:** `xinas_menu/screens/mcp.py` `_restart` captures `ok` per service into the rendered line, then logs `self.app.audit.log("mcp.restart", "xinas-nfs-helper", "OK")` unconditionally, and heads the view with `"Services restarted:"` in green regardless. A restart that failed is recorded in the audit trail as a success — the one place an operator looks to reconstruct what happened.

- [ ] **Step 1: Spec first.** In `docs/Management/audit-log-spec.md`, after the "Control-path row → display line" table, add:

```markdown
### Writer contract — STATUS is an observation, not a formality

The rendering rules above are only worth as much as the values writers put in.
Every local `audit.log` writer must pass the **observed** outcome as STATUS:
`OK` only when the operation it names actually succeeded, `FAIL` otherwise. A
writer that hardcodes `OK` makes the audit trail actively misleading — it is
the one record an operator reconstructs an incident from, and a failed action
recorded as a success is worse than no record at all, because it is trusted.

Where an action fans out over several units or resources, STATUS is `OK` only
when **all** of them succeeded; the per-item detail belongs in the rendered
view, not in the STATUS column.
```

#### 2b — OS disk on an LVM/MD/ZFS root is not flagged

**Why this is real:** `xinas_menu/api/grpc_client.py` `_get_os_drives` inspects `dev["children"]` one level deep. A guided-LVM, dm-crypt, or MD root exposes `/` on a **grandchild** (`disk → part → lvm`), so the OS disk is not added to `os_drives`, is not flagged `system` in the drive list, and appears in `DrivePickerScreen` as available for a new array. This is the TUI-side twin of the installer bug fixed in commit `691ef7d`, which resolved OS mounts through `lsblk --inverse` for exactly this reason; see `docs/Installer/raid-spec.md` §2 for that writeup.

#### 2c — a remediation command can hang the wizard forever

**Why this is real:** `xinas_menu/health/remediation.py:288` runs `subprocess.run(action.command, capture_output=True, text=True)` — no `timeout`, and stdin inherited from the TUI process. A fix command that waits on input, or simply never returns, blocks the wizard with no way out.

- [ ] **Step 1: Spec first.** Create `docs/HealthCheck/remediation-spec.md`:

```markdown
# Health-Check Remediation — Execution Contract

`xinas_menu/health/remediation.py` turns a health-check finding into an
optional automated fix. `RemediationWizard.apply(action)` either applies a
structured `nfs_conf_fix` or shells out to `action.command`.

## Running `action.command`

Remediation commands run **unattended, from inside the TUI process**. Two
properties follow, and both are contract rather than implementation detail:

1. **Bounded.** The command runs with a timeout (`_COMMAND_TIMEOUT`, 120 s).
   On expiry `apply` returns `(False, "timed out after 120s: <command>")`.
   Without a bound, one command that never returns hangs the wizard with no
   way out — the health screen is the surface an operator reaches for when
   the system is *already* misbehaving, so "the fix command wedged" is not a
   remote scenario.
2. **Never interactive.** stdin is `subprocess.DEVNULL`. A command that
   prompts must fail fast on EOF rather than block forever on a terminal the
   wizard is not driving. Remediation commands that genuinely need operator
   input do not belong here; they belong in the finding's `fix_hint` text.

`apply` returns `(ok, detail)` where `detail` is stderr, falling back to
stdout. A non-zero exit is a normal failure, not an exception.
```

**WS5.3 is only partly discharged, and the note must say so.** Its second half
— "make teardown workers `exclusive=True` and non-cancellable by stray input" —
**did not survive re-baselining** and is deliberately not implemented. `TaskCancelled`
subclasses `TaskFailed`, which subclasses `ControlPathError`, so the teardown's
`except ControlPathError` in `_delete_array` already catches a cancellation and
surfaces it through `_teardown_failed`; the final destroy step handles
`TaskCancelled` explicitly and passes a `cancel_check`. Nothing cancels silently.
The only residual is cosmetic: a cancellation during steps 1–2 is *labelled* as a
failure. Record that in the status note as verified-not-reproduced, with the
reasoning, so the next reader does not re-open it from the finding table alone.
