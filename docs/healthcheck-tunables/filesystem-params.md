# Filesystem Parameters — Health Check Tunables

XFS mount options and mkfs parameters verified by the xiNAS health check engine.
These settings are applied automatically by the `raid_fs` and `nvme_namespace` Ansible roles.

**Source of truth:** the semantics below are quoted from
[`xfs(5)`](https://man7.org/linux/man-pages/man5/xfs.5.html) (Linux man-pages)
and [`mount(8)`](https://man7.org/linux/man-pages/man8/mount.8.html) for the
generic VFS options. The "why it matters" column is xiNAS's *rationale* for
choosing the option on this workload — that part is our reasoning, not a
kernel guarantee, and is marked where it goes beyond the man page.
Last reconciled against `xfs(5)` on 2026-08-14.

## XFS Mount Options

`noatime` and `nodiratime` are **generic VFS options** handled by `mount(8)`,
not XFS options — `xfs(5)` does not list them. `mount(8)` also notes that
**`noatime` implies `nodiratime`**, so specifying both is redundant (harmless,
and it does make both appear in `/proc/mounts`, which is what the check reads).

All data filesystems are mounted under `/mnt/` with options generated by the
`nvme_namespace` role (`generate_raid_config.yml`). The health check reads
`/proc/mounts` and verifies each option is present.

| Option | Recommended | Why it matters | How to check | Remediation |
|--------|-------------|----------------|--------------|-------------|
| `noatime` | present | Prevents metadata writes on every read — critical for NFS serving where clients generate millions of reads | `grep /mnt /proc/mounts` | Add `noatime` to mount options in `/etc/fstab` or systemd mount unit |
| `nodiratime` | present | Disables atime updates on directory access — reduces metadata I/O for directory-heavy NFS workloads (ls, find) | `grep /mnt /proc/mounts` | Add `nodiratime` to mount options |
| `logdev=<device>` | present (e.g., `/dev/xi_log`) | Separates journal writes from data I/O onto a dedicated RAID-10 log array — eliminates journal contention on the data disks | `grep /mnt /proc/mounts` | Requires `mkfs.xfs -l logdev=...` at filesystem creation time; cannot be changed post-creation without reformatting |
| `logbsize=256k` | `256k` | Sets the size of each in-memory log buffer. `xfs(5)` gives the default as 32768 (32k) for version-1 logs and lists 256k as a valid size for version-2 logs only — raising it reduces log flushes for sequential writes | `grep /mnt /proc/mounts` | Add `logbsize=256k` to mount options |
| `allocsize=131072k` | `131072k` (128 MB) | `xfs(5)`: "Sets the buffered I/O end-of-file preallocation size when doing delayed allocation writeout." Valid range is page size through 1 GiB in power-of-2 increments — 128 MiB qualifies. Reduces fragmentation for the large sequential writes typical of NFS/AI workloads *(rationale, not a man-page claim)* | `grep /mnt /proc/mounts` | Add `allocsize=131072k` to mount options |
| `largeio` | present | `xfs(5)`: with `largeio` **and a stripe width configured**, the stripe width is what `stat(2)` returns in `st_blksize`; otherwise `allocsize` is used. The default is `nolargeio`. Only meaningful because `mkfs` set `sunit`/`swidth` below | `grep /mnt /proc/mounts` | Add `largeio` to mount options |
| `inode64` | present | `xfs(5)`: allows inodes anywhere in the filesystem, with inode numbers exceeding 32 bits; **"For kernel v3.7 and later, inode64 is the default."** So this is belt-and-braces, not a fix | `grep /mnt /proc/mounts` | Add `inode64` to mount options |
| `swalloc` | present | `xfs(5)`: "Data allocations will be rounded up to stripe width boundaries **when the current end of file is being extended and the file size is larger than the stripe width size**." Note the two preconditions — it is not blanket stripe alignment for every allocation | `grep /mnt /proc/mounts` | Add `swalloc` to mount options |

### Claims corrected on 2026-08-14

Three descriptions above asserted kernel behaviour that `xfs(5)` does not
support. Recorded here so the same wording doesn't come back:

- **`largeio` "NFS clients use this to optimize transfer sizes"** — removed.
  `xfs(5)` scopes the effect to `st_blksize` from `stat(2)` on the server.
  Linux NFS clients negotiate `rsize`/`wsize` with the server's configured
  maximum; nothing in `xfs(5)` or `nfsd` documentation says the exported
  filesystem's `st_blksize` drives that negotiation. The option is still worth
  setting for local and application-visible I/O hints, which is the claim that
  survives. `pathconf()` was also dropped — `xfs(5)` mentions only `stat(2)`.
- **`inode64` "inodes are constrained to the first 1 TB"** — softened.
  `xfs(5)` says `inode32` limits inode *numbers* to 32 bits; the 1 TiB figure
  is a **[inferred]** consequence of that limit at typical inode sizes, not a
  documented number. The load-bearing correction is the other half: `inode64`
  has been the **default since kernel v3.7**, so the option is not preventing
  a failure on any supported platform.
- **`swalloc` "forces stripe-aligned allocation"** — narrowed to the man
  page's two preconditions (extending EOF, file larger than the stripe width).

## XFS Stripe Alignment (mkfs parameters)

Set at filesystem creation time via `mkfs.xfs -d su=<strip_size>k,sw=<stripe_width>`.
Cannot be changed without reformatting.

| Parameter | Recommended | Why it matters | How to check |
|-----------|-------------|----------------|--------------|
| `sunit` (stripe unit) | Non-zero, matching RAID strip size | Aligns allocation unit with RAID strip size — misalignment causes read-modify-write penalties on every I/O | `xfs_info /mnt/<mountpoint>` — look for `sunit=N` (in 512-byte blocks) |
| `swidth` (stripe width) | Non-zero, matching RAID data disks x strip size | Aligns full-stripe writes — enables the RAID controller to write entire stripes without read-modify-write | `xfs_info /mnt/<mountpoint>` — look for `swidth=N` (in 512-byte blocks) |

**Typical values:**
- Data array (RAID 5, 128 KB strip): `sunit=256` (128 KB / 512), `swidth=256 * (N-1)` where N = drive count
- Log array (RAID 10, 16 KB strip): `sunit=32` (16 KB / 512), `swidth=32 * (N/2)`

## XFS Quota

| Parameter | Recommended | Why it matters |
|-----------|-------------|----------------|
| `uquota` | present | Enables user quota tracking — required for per-user space accounting on NFS exports |

## Health Check Integration

- **Section**: `filesystem`
- **Check names**: `mount_opts` (existing, checks noatime), `xfs_mount_opts` (new, checks all options above), `xfs_stripe_align` (new)
- **Profile coverage**: `xfs_mount_opts` in standard+deep; `xfs_stripe_align` in deep only
- **Severity**: Missing options → WARN; missing stripe alignment → WARN
- **Source files**: `collection/roles/nvme_namespace/tasks/generate_raid_config.yml`, `collection/roles/raid_fs/tasks/create_fs.yml`
